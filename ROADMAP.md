# ROADMAP — очередь улучшений бота

Облачный Claude запускается 3 раза в день и берёт **первую невыполненную** задачу из «Очереди».
Протокол — в `CLAUDE.md`. Выполнено: `[x]` + дата + одна строка итога. Большую задачу дробить: сделать
первую часть, остаток — новой строкой сразу под ней.

## Идеи
_(облачный Claude добавляет сюда предложения, когда очередь пуста)_
- Резервные источники обменников на случай, если BestChange API снова недоступен (исследование 2026-09-25): (1) официальный BestChange API v2 (`https://bestchange.app/v2/{apiKey}/rates/...`, JSON, до 500 направлений за запрос) — нужен бесплатный ключ, который владелец получает сам в кабинете BestChange («Профиль → API для получения курсов»); адаптер писать после появления `BESTCHANGE_API_KEY` в .env, форма ответа — в `https://bestchange.app/en/openapi.yaml`; (2) TopEx (`top-ex.org`, один GET на направление, курс/min/max/резерв во встроенном JSON, без ключа, но не API и без явного разрешения парсинга — только редкие запросы и сверка курса со вторым источником); не брать: kurs.expert и rates.guru (парсинг запрещён), ExchangeSumo/Exnode (JS-антибот), HTML-страницы bestchange.ru (условия запрещают пауков).
- Резервное копирование SQLite/JSON-баз (`data/trades.db`, `history.db`, `alerts.db`, `blacklist.db`,
  `keys.json`, `presets.json`) — раз в сутки (например, на выходе из тихих часов) копия в `data/backup/`
  с ротацией последних N штук. Атомарная запись через `jsonstore.py` защищает от повреждения при записи,
  но не от порчи диска/случайного удаления файла — короткая копия рядом дала бы восстановление без сети
  и без новых внешних зависимостей.
- Watchdog всего цикла сканирования: `Bot.check_venues` уже алертит про отдельную зависшую площадку, но
  необработанное исключение или зависание в `scan_loop` целиком (например, в `_stack`/`reliability`, не
  в сетевом адаптере) сейчас не даёт отдельного сигнала — бот молчит, пока пользователь не заметит
  отсутствие сигналов. Нужен таймер «последний успешный `scan()` был больше N минут назад» с алертом
  в Telegram, отдельным от алертов по конкретным площадкам.
- `/stats`: разбивка прибыли по направлению (площадка-покупка → площадка-продажа), а не только по периоду
  день/неделя/месяц — по факту сделанных сделок из `trades.db` (не по снимкам, как `history.backtest`),
  чтобы видно было, какие пары реально приносят деньги пользователю, а не только средний процент по всем.
- Ключи бирж (`data/keys.json`) сейчас хранятся в открытом JSON — `key`/`secret`/`passphrase` читаемы
  любым, кто получил доступ к файлу на диске. `accounts.save_key`/`keys()` могли бы шифровать эти поля
  (например, `cryptography.Fernet` от мастер-пароля, который владелец вводит в боте один раз за запуск
  и который держится только в памяти процесса) — без новых внешних доменов и без subprocess. Главный
  открытый вопрос — где хранить мастер-пароль между перезапусками launcher'ом (спрашивать при каждом
  старте неудобно, а хранить рядом в `.env` обнуляет смысл шифрования), поэтому сначала стоит обсудить
  компромисс с владельцем, прежде чем браться за реализацию.
- `blacklist.py` хранит только `(ex, nick)` — без даты добавления и причины, поэтому `/blacklist` не
  показывает, когда и почему мерчант попал в список, и нет способа заметить, что запись могла устареть
  (мерчант мог исправиться за месяцы). Добавить колонки `added_ts`/`note` (причину — опциональным текстом
  после кнопки «🚫», как ввод суммы у `/calc`) и показывать в `/blacklist` возраст записи «в списке N дней»
  — не снимать автоматически, само решение снимать/нет остаётся за владельцем. (сделано 2026-09-26)
- Сухой прогон (`paper.py`) сейчас сверяет план с фактом только внутри своих виртуальных кругов, но не
  с тем, что владелец реально делал руками в тот же период (`trades.db`, факт из `trades.set_fact`).
  В `/paper report` можно добавить сравнение — те же площадки/пары/окно времени — насколько предположения
  модели сухого прогона (объявление и глубина стакана ещё на месте на момент каждой стадии) совпадают с
  тем, что получилось на настоящих сделках; это ровно тот вопрос, от которого зависит решение о переходе
  на этап 2. (сделано 2026-09-26)
